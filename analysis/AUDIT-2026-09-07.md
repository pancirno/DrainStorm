## Conclusion

The reconstruction is not yet gameplay-equivalent to the Win16 executable. This pass found eleven concrete engine/message discrepancies and a regression-test isolation/oracle problem. Several affect shared systems, so they can change many otherwise correctly reconstructed boards.

No production source, executable in `reconstructed/bin`, or game assets were changed. The audit adds this report and a diagnostic harness. Findings below distinguish direct executable evidence, decompiled control flow, and new C++ safety issues.

## Findings

### 1. P1 — Enemy collisions are resolved in the wrong order

Location: [game_data.cpp:5402](C:/Projekty/ds/reconstructed/src/game_data.cpp:5402), also the call sequence at [2170](C:/Projekty/ds/reconstructed/src/game_data.cpp:2170).

`AdvanceActors` moves the entire actor array, then runs a second pass for actor/projectile collisions. Its caller finally resolves actor/player collisions. Original `FUN_1008_8310` instead completes movement and collision processing for **each actor** before advancing to the next actor. In particular, the player-coordinate check calls `2920` and removes the actor before the alternative projectile-collision branch.

Consequences: an enemy entering the player's square can be killed by a coincident projectile without hurting the player; actors killed earlier in the turn continue blocking destinations while later actors move; splitting enemies and projectile consumption happen at different times. The original also bypasses that actor's collision processing after its terrain-breaking branch, whereas the new second pass does not.

Diagnostic: an actor entering a player/fireball square leaves native health at 3; the original branch subtracts one, leaving 2. Reference: [decompiled.c:9798](C:/Projekty/ds/analysis/export/decompiled.c:9798), especially `LAB_1008_864d` and its player-before-projectile branches.

### 2. P2 — Fireballs have lost their surrounding-cell attack

Location: [game_data.cpp:5087](C:/Projekty/ds/reconstructed/src/game_data.cpp:5087).

The native loop only considers an actor at exactly the projectile coordinates and stops at the first match. Original `1008:790c–79f7` handles type-4 projectiles against every actor within one cell on each axis. Types 0, 1 and 4 are affected throughout that neighborhood; types 2 and 3 have a distance-dependent random check away from the center. Successful fireball attacks continue scanning actors.

Diagnostic: a type-0 enemy adjacent to the fireball's new position survives natively; it must die in the original. The raw instructions confirm the two absolute-distance comparisons against 1, the actor-type tests, and the continued scan.

### 3. P1 — Fireballs can destroy terrain that should stop them intact

Location: [game_data.cpp:5142](C:/Projekty/ds/reconstructed/src/game_data.cpp:5142).

The native solid-tile branch calls `DamageBoardSquare(..., 4)` for fireballs. In original `FUN_1008_77d0`, the blocked-tile branch removes projectile types **0 and 4 without invoking the destruction callback**. Only types 1 and 2 dispatch the ordinary impact callbacks here.

Diagnostic: a fireball hitting tile 3 changes it to tile 0 natively; the original retains tile 3. This can alter obstacles, routes, drops, and progression. Reference: [decompiled.c:9490](C:/Projekty/ds/analysis/export/decompiled.c:9490), `LAB_1008_7c60` onward.

### 4. P2 — Mouse controls and identification are disabled on playable descendants

Locations: [game_data.cpp:2608](C:/Projekty/ds/reconstructed/src/game_data.cpp:2608), [2622](C:/Projekty/ds/reconstructed/src/game_data.cpp:2622), [2412](C:/Projekty/ds/reconstructed/src/game_data.cpp:2412).

These guards use `rootBoard_`, and `HandleBoardTransition` sets that flag false on children. Original `6048` and `60f4` test the board word at **+0x0c**, which is the scripted/demo flag, not ancestry. The keyboard handler `6f46` uses the same word to select scripted input. Parent linkage is the far pointer at **+0x0e/+0x10**, visible in the board-loading/linking code.

Consequently, descending disables click-to-move, Shift-click item use, and right-click descriptions, even though keyboard gameplay continues. The application already rejects mouse actions during demo mode; ancestry must not be used for that distinction. Diagnostic: a playable child rejects even a click-to-wait on the vessel.

The regression at [game_data_tests.cpp:126](C:/Projekty/ds/reconstructed/tests/game_data_tests.cpp:126) explicitly asserts this incorrect behavior. The death-handling comment in `application_state.cpp` already recognizes the correct +0x0c interpretation, making the implementation internally inconsistent too.

### 5. P2 — Random containers use incorrect Triple-Shot Cannon eligibility

Location: [game_data.cpp:3464](C:/Projekty/ds/reconstructed/src/game_data.cpp:3464).

Original `1008:a1c8–a270` has these gates:

| Container | Original | Reconstruction |
|---|---|---|
| Type 1 | No cannon; roll 12 equals 6; depth >=3, or depth 2 plus roll 5 equals 5 | No cannon and roll 12 equals 6; no depth gate |
| Type 2 | Roll 3 equals 3; depth >=3; **no cannon** | Roll 3 equals 3; **already has cannon**; no depth gate |

The ownership test is inverted in type 2. Missing gates also change RNG consumption, shifting subsequent gameplay randomness. Diagnostic: type-1 treasure at procedural depth one grants the cannon with RNG seed 1; that branch is forbidden at depth one in the original. Raw comparisons use the board's +0x3c depth word, not the native board-selector number.

### 6. P2 — Xoid Fortress random placement still has three translation errors

Location: [game_data.cpp:836](C:/Projekty/ds/reconstructed/src/game_data.cpp:836).

Original `1010:3406–3431` performs **2 × (difficulty + 2)** attempts, draws column `random(38)` and row `random(34)`, and passes both directly to `1008:c40a`. That helper indexes `[column][row]` and only writes an empty cell.

The reconstruction always performs six attempts, assigns the 38-range roll to row and the 34-range roll to column, and subtracts one from both. Thus difficulty 2–4 under-generates these objects and consumes too few random values; even difficulty 1 has wrong coordinates, including rejected rows 36–37. The corrected central Fortress geometry does not fix this surrounding-generation discrepancy.

References: [decompiled.c:15365](C:/Projekty/ds/analysis/export/decompiled.c:15365), [12902](C:/Projekty/ds/analysis/export/decompiled.c:12902); confirmed against raw constructor instructions.

### 7. P2 — Bubbles pass through immune enemies instead of being consumed

Location: [game_data.cpp:5088](C:/Projekty/ds/reconstructed/src/game_data.cpp:5088).

For projectile type 0 against actor type 2 or 3, `affected` is false and `removeProjectile` remains false. Original `1008:7a1d–7a2a` branches to `7ba6`, which deletes the projectile without deleting the enemy. Native post-actor collision code does consume these bubbles, so the outcome incorrectly depends on which side moves into the collision.

Diagnostic: a moving bubble hitting a stationary type-2 actor leaves one projectile natively; the original leaves none.

### 8. P2 — Rejected casino wagers do not consume a world turn

Location: [game_data.cpp:2849](C:/Projekty/ds/reconstructed/src/game_data.cpp:2849).

Closed-table, already-bet, unsupported-item, mixed-item and maximum-bet branches return immediately. They bypass projectiles, board callbacks, spawning, actor movement, repellent drain and turn counting. Original `FUN_1008_1b22` calls the world-update sequence after `FUN_1008_1fe2` returns, including after the casino item callback rejects an action.

Diagnostic: an attempted wager at a closed table returns success but leaves turn count 0; the original accepted directional item action advances a turn. The ordinary non-casino failure path already implements that rule.

### 9. P2 — All three special-key pickup messages identify the wrong key

Location: [game_data.cpp:3493](C:/Projekty/ds/reconstructed/src/game_data.cpp:3493).

| Overlay | Inventory class (already correct) | Original message | Native message |
|---|---:|---|---|
| 4 | 17 | Moon Key | Star Key |
| 5 | 16 | Star Key | Fire Key |
| 6 | 18 | Fire Key | Moon Key |

Raw branches at `a2b4`, `a2d1`, `a2ee` load string offsets `d188`, `d158`, `d170`, respectively. Those null-terminated strings were read directly from the original executable. Fix the labels, not the inventory mapping.

### 10. P2 — Casino follow-up messages are concatenated and then truncated

Location: [game_data.cpp:4288](C:/Projekty/ds/reconstructed/src/game_data.cpp:4288), through the bonus-prize branches.

The winner notice, retaliation notice and bonus/closure notices are appended to one `pendingMessage_`. `RecordGameplayMessage` retains only its first 99 characters. A winner notice plus retaliation plus a treasure-room bonus exceeds that limit, so later instructions disappear rather than becoming reviewable messages.

Original `1010:1180` uses separate message submissions, including `2822` calls at `1764`, `17bb`, `1805` and `1822`. The 99-character limit is per original message, not per concatenated turn. This is another instance of the message issue previously seen with cookies/signposts.

Related structural risk: the remaining scalar message assignments can overwrite earlier notices; `TakeMessages` appends the scalar after the vector regardless of chronological order. A unified ordered event queue would address that, but every original submission boundary should be verified during the fix.

### 11. P2 — More than twenty messages in one batch produce an invalid history index

Location: [application_state.cpp:186](C:/Projekty/ds/reconstructed/src/application_state.cpp:186).

History retains twenty entries, but `TakeGameplayMessage` subtracts the full incoming batch length minus one from the final cursor. For 21 messages, cursor 19 becomes `SIZE_MAX`, and the following unchecked `operator[]` is out of bounds.

This is a native safety bug, not simply an original-game parity difference. A large same-turn pickup batch can be represented by the accepted save format; the loader permits overlapping overlay records. Ordinary gameplay frequency is not established. The harness demonstrates the index arithmetic without deliberately executing the invalid dereference. Original `55e0` adjusts its retained-message cursors as old entries are evicted.

### 12. P2 — The regression suite is not an independent or isolated parity oracle

Locations: [game_data_tests.cpp:29](C:/Projekty/ds/reconstructed/tests/game_data_tests.cpp:29), [126](C:/Projekty/ds/reconstructed/tests/game_data_tests.cpp:126), [3273](C:/Projekty/ds/reconstructed/tests/game_data_tests.cpp:3273).

The tests derive the production `reconstructed/bin/DrainStorm.exe` path from the asset directory. Application fixtures therefore load the player's `DRAIN64.SCO` and `DRAIN64.KEY`, while some tests assume an empty score table and default bindings. On this workspace the normal CTest run fails at the zero-score/empty-slot assertion. Running the same binary against a copied asset tree and clean sibling `bin` passes.

Additionally, the descendant mouse test encodes the same wrong field interpretation as the implementation. Passing it is evidence of consistency with the test, not with the original executable.

Recommended correction: all fixtures and sidecars should live under a fresh per-run directory; parity expectations should cite recovered branches and cover the counterexamples above. Do not delete the player's score table to make tests pass.

## Coverage and limits

This is a static cross-module audit with targeted executable-level verification and synthetic native-state probes, **not a certification that every recovered instruction or board is equivalent**. Review covered the shared movement/item/projectile/actor paths, input and lifecycle plumbing, messages, save/load and board graph interfaces, resource/rendering code, high scores, and selected constructors/runtime callbacks. The detailed Fortress, pickup, projectile and input findings were checked against their original functions; other board-specific paths were sampled, not exhaustively replayed.

The isolated existing tests exercise many additional board-specific cases, including the recent signpost/cookie work, but inherit their expectations from the reconstruction. They are not a differential run against Win16. No live original-game replay, complete all-difficulty/all-seed map comparison, or visual/timing equivalence test was performed.

Do not classify intended Win64 adaptations as bugs automatically: native save/score/key formats, direct modern windowing, buffered rendering and nonblocking animation scheduling differ by design. However, scheduling and data-format changes still need explicit compatibility boundaries and tests. In particular, shared transient-animation age and saved board/message state warrant further parity work.

The reconstruction notes' broad completion claims should not be treated as a verified function-by-function ledger. The priority is to correct shared turn semantics and projectile behavior, then mouse/demo separation, loot/depth and generation rules, and message handling. After that, compare deterministic whole-turn snapshots and every board constructor at all four difficulties against an independent original-code reference.
